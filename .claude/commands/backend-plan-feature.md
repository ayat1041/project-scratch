# Plan Backend Feature

Produces a build plan. Creates no files. Run before `/scaffold-module`.

## Step 1 — Gather inputs

Confirm (ask if missing, do not guess):

- Domain (`auth` | `user-management` | `platform` | `common`)
- Feature name (kebab-case)
- The endpoints: method, path, who calls them, what they return
- Does it need new tables or columns?
- Does it need async work (email, ingestion, sync)?
- Does the frontend or admin consume it? Which one?

If an FRD/TDD exists for this feature, read it first and take the answers from there.

## Step 2 — Required reading

- Skill `backend-architecture`
- `.github/instructions/api-workflow.instructions.md` §11
- `.github/instructions/backend-file-structure.instructions.md`
- `apps/backend/SKILL.md`

## Step 3 — Allocate the feature ID

List `src/modules/<domain>/features/` and take the next free number in that domain's series — `F1xxx` auth, `F5xxx` common, `F6xxx` user-management, `F9xxx` platform. State the ID and the series you took it from. Never invent a new prefix.

## Step 4 — Decide the layers

State **needed / not needed** and why for each:

- `<feature>.routes.ts` — always
- `controllers/` — always
- `services/` — always
- `validations/` — needed unless every endpoint is a param-only read
- `swagger-docs/` — always
- `types/` — only when a contract is shared beyond the feature
- `tests/integration/` — when service-level behaviour exists
- Feature-local `policies/` — only when the rule is not expressible by an existing `src/policies/<domain>.policy.ts` action

Then, outside the feature:

- New domain queries/commands in `src/domain/<domain>/<sub>/models/`?
- New policy action on an existing `<domain>.policy.ts`?
- New permission in `@repo/constants`?
- New schema/response type in `@repo/schemas-types`?
- New table/column in `src/db/schema/`?
- New queue, routing key, or consumer?

## Step 5 — Map each endpoint

One row per endpoint:

| Method + path | Permission | Existence fn | Policy action | Controller | Service | List? |
|---|---|---|---|---|---|---|

For each, confirm the middleware chain is the standard `isAuthenticated → hasPermission → resolveResources → authorize → controller`, and flag any endpoint that genuinely cannot use it, with the reason.

Apply the **redundant-param rule**: if a resource carries `organizationId`, the route resolves only the resource id.

Mark every list endpoint — those follow `backend-list-endpoints`, not a bespoke shape.

## Step 6 — Identify contract gaps

List every payload schema, response type, entity type, shared constant, and permission that must exist and does not. Each becomes a `/frontend-contract`-style change in `packages/` before backend code is written.

Name the client apps that will consume this feature, so the contract is designed once for all of them.

## Step 7 — Report the build order

```
0. packages/    schemas, response types, constants, permissions
                → pnpm --filter @repo/schemas-types build
1. /db-change   tables/columns  → db:generate → REVIEW SQL → db:migrate
2. /scaffold-module <domain> <F-ID>-<feature>
3. /backend-query   existence fns + domain queries/commands
4. /backend-policy  policy actions + permission wiring
5. /create-endpoint one endpoint at a time (route + validation + controller + service)
6. /backend-worker  queue + consumer, if async work is in scope
7. /add-swagger-doc if not generated by /create-endpoint
8. /generate-tests (TDD-gated) or /generate-integration-tests
9. /backend-audit
10. /backend-verify
11. /spec-sync <feature>
```

Flag any open question that would change the plan, and stop for an answer rather than assuming an endpoint contract.
