# Generate Integration Tests (lightweight)

Use this when you want service-level integration tests (`node:test` + real DB) and you do **not** have a formal TDD/issue artifact. For the full TDD-gated, layer-routed path, use `/generate-tests` instead.

**Scope:** this command produces **Layer 2 component (service) tests only** — the §13.1 "Backend" acceptance-criteria layer. It does **not** produce API E2E tests; cross-cutting ACs (auth / tenant / permission / not-found / contract — FRD §13.3, `AC-18`–`AC-22`) require the full middleware chain and must go through `/generate-tests` + Playwright.

## Test-case ID band scheme (shared convention)

Every test name is prefixed with a feature-scoped, **band-numbered** TC id: `F<feat>-TC-<NNNN>: <intent>`. Bands keep parallel authors (devs vs SQA) in disjoint number ranges so no two teams collide on the same id.

| Band | Layer | Owner | Generated by |
| --- | --- | --- | --- |
| `0xxx` | Unit (pure logic) | Backend dev | `/generate-tests` (or hand) |
| `1xxx` | Integration (backend service + real DB) | Backend dev | **this command** / `/generate-tests` |
| `2xxx` | API E2E (backend, full middleware chain) | SQA | `/generate-tests` |
| `3xxx` | Frontend component / integration | Frontend dev | frontend suite |
| `4xxx` | Frontend / UI E2E | SQA | frontend suite |

**Sub-blocking within a band:** give each service file its own century block and leave gaps for inserts — e.g. for api-keys integration tests: `revoke` → `1001…`, `create` → `1101…`, `rotate` → `1201…`, `delete` → `1301…`. This command emits **`1xxx` ids only** (it owns the integration layer); never emit `0xxx`/`2xxx`/`3xxx`/`4xxx`.

## Step 1 — Gather inputs

Confirm (ask if missing):

- Target service file(s) (e.g. `apps/backend/src/modules/user-management/roles/services/role.service.ts`).
- Actions to cover (default: every exported function).

## Step 2 — Check for an FRD (traceability hook)

Look for a feature FRD near the target (`.../<feature>/docs/*-frd.md`).

- **If an FRD exists:** read its §13.1 backend AC table. Map each service behavior you are about to test to the `AC-N` it satisfies, and **stamp those markers** (Step 4). This keeps the AC-traceability invariant (`scripts/check-spec-drift.ts`) green even on the lightweight path, and lets `/spec-sync` reconcile afterward.
- **If no FRD exists:** proceed purely code-driven (the real purpose of this command). No AC markers are required because there is no AC contract to satisfy yet. Note this in your report.

## Step 3 — Required reading

- `.github/instructions/testing-backend.instructions.md`
- `.github/instructions/testing.instructions.md`
- The target service file and its schema/validation imports.
- One existing integration test in the same module for style alignment (e.g. files under `apps/backend/src/modules/user-management/F6003-api-keys/tests/integration/` or `apps/backend/src/modules/user-management/permissions/tests/integration/`).

## Step 4 — Generate

For each service action create `<feature>/tests/integration/<action>.service.test.ts`:

- `node:test` + `node:assert/strict`.
- `uid()` helper for every unique DB field.
- `before` seeds dependencies; `after` deletes join rows first, then parents, then `await closeDbPool()`.
- Cover the success path (with DB read-back assertion) + every typed error path (`ERROR_TYPES.*` / error-`code` predicate).
- Cover every validation category and every state transition the service actually implements.
- For list services: pagination + search filter cases.
- **Stamp banded TC ids.** Name every test `F<feat>-TC-<NNNN>: <intent>` using the **integration band (`1xxx`)** from the band-scheme table above. Allocate one century block per service file (gaps reserved): first integration file in the feature → `1001…`, second → `1101…`, and so on. If the file already has banded ids, continue its block; if it has unbanded/legacy ids (e.g. `TC-0001`), renumber them into the `1xxx` block.
- **When an FRD was found (Step 2):** add a header block listing the FRD reference + the `AC-N` markers this file covers, and an inline `// AC-N: <intent>` on each relevant test — matching the existing api-keys integration tests. The banded `F<feat>-TC-1NNN` id lives in the test name; the `AC-N` marker stays in the inline comment, so one AC can own many TCs.

## Step 5 — Verify

From `apps/backend`:

- `pnpm run build` must pass.
- If the docker dev stack is up, run the new files via `tsx --test <paths>` and report pass/fail.

## Step 6 — Report

- New test files as workspace-relative links.
- Whether an FRD was found and which §13.1 ACs were stamped (or "no FRD — code-driven, no AC markers").
- The `F<feat>-TC-1NNN` id range allocated per file.
- Build result + command to run the tests locally.
- If an FRD was found, remind the user to run `/generate-tests` for the §13.3 API-E2E ACs and `/spec-sync <feature>` to reconcile the docs.
