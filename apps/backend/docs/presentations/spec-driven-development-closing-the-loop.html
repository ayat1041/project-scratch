Spec-Driven Development What it is, why it works, and how we build with it.

Definition

What is Spec-Driven Development?

A development methodology where a precise, reviewed specification is the authoritative source of truth — written and approved before implementation, and kept aligned with the code as it evolves.

Code, tests, and documentation are derived from and traceable to the spec — not the other way around.

The core idea

The spec is the contract, not decoration

  • Progressive refinement — intent becomes a functional spec, then a technical design, then concrete tasks.
  • Ambiguity resolved up front — decisions are made when they're cheap (in a document), not late (in production).
  • One source of truth — every fact has a single owning artifact; everything else references it.
  • Living, not frozen — the spec is reconciled with the code so it stays true over time.

Benefits

Why spec-driven development

  • Less rework — build the right thing once; mistakes are caught on paper.
  • Parallel execution — teams work concurrently against a shared, stable contract.
  • Trustworthy AI output — agents generate from accurate specs, correctly, at scale.
  • Faster onboarding — documentation you can actually trust.
  • Audit-ready — every requirement traces to code, tests, and API docs.
  • Quality by construction — consistency is enforced, not hoped for.

How our flow works · lovable FRD stage

Surface conflicts early, before FRD

  • The lovable FRD is generated from product UI + workflow docs — the only stage where both are in context together.
  • We explicitly capture Source Conflicts when UI and docs disagree — never silently pick a winner.
  • We capture Open Questions where neither source answers — marked for product decision.
  • These flow forward to the engineering FRD marked by ID so nothing gets lost or forgotten.
  • Result: ambiguities surface at the cheapest point — before engineering time is spent.
How our flow works · requirements traceability

FR and AC linked bidirectionally

  • Every Functional Requirement explicitly links to the Acceptance Criteria that verify it.
  • Every AC links back to its FR — so relationships are visible and complete.
  • Gaps are impossible to hide: untested FRs and orphaned ACs surface immediately.
  • Example: FR-7: sort by updatedAt → AC-3: rows sorted desc by updatedAt
  • This is baked into our FRD authoring guide — every new FRD follows it by default.
How our flow works · test traceability

Tests linked to acceptance criteria

  • Every test case declares which AC(s) it validates — via a comment header and inline AC labels.
  • This completes the traceability chain: Requirement → Spec → Test Code — all navigable by ID.
  • Finding what breaks when a spec changes: grep "AC-5" *.test.ts → all affected tests.
  • Coverage gaps are visible: AC with no test comment = unverified requirement.
  • Result: 100% of requirements trace end-to-end, and impact analysis is instant.
How our flow works · standardization

Consistent naming and structure amplify SDD

  • Naming conventions — entity-first files, camelCase functions, SCREAMING_SNAKE_CASE constants — so code intent is obvious without reading it.
  • File structure — consistent routes/controllers/services/validations boundaries — so the codebase matches the architectural diagram.
  • API workflow — middleware order, permission flow, resource resolution — so every endpoint is built the same way.

Why this matters

  • Specs map to code locations by pattern
  • AI agents generate consistently
  • Code review finds deviations instantly
  • New team members onboard by pattern
  • Drift detection is automated
How our flow works · the gate

Reviewed before a line is written

  • The FRD is signed off by Product, QA, and Engineering before implementation begins.
  • Business what and technical how live in separate documents — never blurred.
  • Non-obvious decisions are logged as ADRs and linked from the specs.
  • This front-loads alignment, so coding starts from agreement, not assumption.

How our flow works · staying true

Specs track the code

  • A reconciliation step keeps specs matching the implementation as it evolves.
  • It reads the actual code — schema, routes, validations — and aligns the docs.
  • Genuine product disagreements are raised for a decision, never silently overwritten.
  • Every document is stamped Last reconciled, so staleness is visible.

What stays in sync

  • State / status values
  • State transitions
  • Validation rules & limits
  • Error messages → HTTP codes
  • Endpoints ↔ API docs
  • Permissions & async behavior
How our flow works · enforcement

Consistency is enforced, not optional

# .github/workflows/backend-ci.yml
- name: Spec drift check
  run: pnpm --filter backend check:spec-drift
  • Our CI blocks any merge that introduces inconsistency — e.g. an endpoint without API docs, or a state in code missing from its spec.
  • Developers get the same check as a fast, non-blocking warning before they commit.
  • Consistency is guaranteed by the pipeline — it doesn't depend on anyone remembering.
Why it matters

Specs are the control plane for AI

  • Our pipeline is AI-assisted at every stage — agents generate by reading the specs.
  • Accurate spec in → correct code, tests, and docs out — automatically.
  • So spec quality is the highest-leverage investment we can make in engineering output.

This is what makes AI a force multiplier — not a liability multiplier.

How our flow works · automation

Specs generate contracts & docs

  • Swagger / OpenAPI is auto-generated from the TDD — schema, endpoints, and request/response shapes are source-of-truth.
  • Technical documentation is generated from code + FRD, describing as-built runtime behavior and state machines.
  • ADRs are captured inline in the TDD §7 (Design Decisions) — the "why" behind technical choices, referenced from specs.
  • Result: no manual doc maintenance — contracts and rationale are always aligned with implementation.
Harness engineering · the bigger picture

Zooming out: harness engineering

Spec-driven development is one piece of a larger discipline — harness engineering: building the whole system around the AI so its capability becomes correct work, reliably and repeatably.

Harness engineering · the core rule

Anything important is enforced, not hoped for

A rule that lives only in someone's memory — human or AI — eventually gets skipped. So every rule we care about is pinned to a level of enforcement, and promoted upward as it proves reliable.

LevelHow it's enforcedStrength
Contextinstruction files the AI auto-readsguidance
Warna heads-up before commit / at session startnudge

  • Heuristics stay as warnings; only mechanical, unambiguous rules become hard gates — so we never train people to bypass the system.

Harness engineering · closing the loop

From "we should" to "the system won't let us not"

  • Tests must trace to requirements — in CI. Every acceptance criterion needs a test, or the build fails. (was a comment convention)
  • The AI's knowledge map can't go stale silently. If code changed but the map didn't, we're warned before trusting it.
  • Specs that fall behind code raise a flag — an automated check counts how far a spec has drifted.
  • Integration tests run in CI against a real database, so "tests pass" is gated, not assumed.
  • We test our instructions, not just our code — see next slide.
Harness engineering · measuring itself

Golden tasks: testing the instructions, not just the code

  • We keep a set of reference tasks (e.g. "build this endpoint") with known-good answers.
  • When we change an instruction, we re-run the tasks and score the output.
  • Score went up? Keep the change. Went down? The "improvement" hurt — revert it.
  • This is the feedback loop for the harness itself — without it, every instruction edit is a blind guess.

Why this matters

  • Tuning stops being guesswork
  • Regressions caught before they ship
  • The harness improves measurably over time
  • Same idea as unit tests — but for our process
Harness engineering · why it matters

The harness is the real product

  • Spec-driven development gives the AI the right input; harness engineering makes sure it produces the right output — every time.
  • As models get more capable, the leverage shifts from the prompt to the harness.
  • The durable edge isn't a clever prompt — it's a better system around the model.

We don't hope the AI does the right thing. We engineer it so it can't easily do the wrong one.

Reality check

The "80-90% faster" claim is overstated

ClaimTrue ForNot True For
80-90% fewer lines of codeBoilerplate, CRUD, controllers, tests, docs ✓Overall time investment ✗
Code review is fasterAI output is consistentScrutiny can be MORE thorough (you must verify AI is correct)
No rework neededLess refactoring for requirements misunderstandingStill need debugging, optimization, edge-case fixes
  • Honest assessment: Overall development time savings are 10-30% (not the claimed 30-50%), and only if specs are excellent.
  • Time saved on code generation is offset by time spent on spec review, code scrutiny, and debugging.
What you actually gain

The REAL value isn't speed — it's quality and certainty

  • Higher quality — AI enforces consistent patterns every time. No style drift, fewer human oversights.
  • Fewer rework cycles — Clear specs eliminate requirement ambiguity. You build the right thing once, not iterate six times.
  • Parallel execution — Stable specs let teams work independently on different features without blocking each other.
  • Full traceability — Every requirement → spec → code → test → doc. Impact analysis and compliance audits are instant.
  • Knowledge preservation — Specs are living documentation. New team members onboard by reading specs, not reverse-engineering code.

The win is predictability and quality, not speed. Speed follows when you don't have to redo things.
